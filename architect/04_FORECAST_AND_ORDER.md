## 예측과 주문안 정책

약품·물품은 별도 벡터로 예측한다. 품목 명단·순서, 목표·환자 문맥, 달력 정의, 체크포인트 revision·해시, 패키지·코드·컨테이너 버전, 장치, 후처리를 `model_version_id`와 실행 manifest에 고정한다. 모델을 자동으로 최신 버전으로 바꾸거나 매주 문맥을 다시 선택하지 않는다.

예측은 원점·대상일·품목·실행별로 저장한다. 다음 주 예측의 겹치는 날짜도 새 실행에 저장하고, 주문 판단에는 해당 시점의 유효한 최신 예측을 명시적으로 연결한다. 미래 실제값을 입력하거나 과거 예측을 실제값으로 수정하지 않는다. 첫 7일·둘째 7일 성능을 구분하고 평가 불가·실패를 남긴다.

주간 정책의 보호기간은 검토주기 `R=7일`과 납기 `L`의 합이다.

```text
목표재고 = 보호기간의 일별 중앙값 예측 합계 + 별도로 정의한 안전재고
가용재고 = 현재 보유 - 사용불가 - 예약 수량
재고위치 = 가용재고 + 유효한 미입고 주문 - 이월 미충족 수요
기본 권고량 = max(0, 목표재고 - 재고위치)
발주량 = 포장단위 올림 후 최소주문량 적용
```

기본 권고량이 0이면 최소주문량을 적용하지 않고 발주하지 않는다. 초기 가상 정책은 신규 부족을 기록하고 이월하지 않으므로 이월 미충족 수요는 0이다. 이후 이월 정책을 추가하려면 예약 수량과 같은 수요를 두 번 차감하지 않도록 정의하고 새 정책 버전으로 검증한다.

초기 납기는 calendar_days만 지원한다. Asia/Seoul 주문 접수일에서 마감시각 이전이면 그날, 마감시각 이상이면 다음 날을 기준일로 정하고 lead_days를 더한 날짜 00:00을 예정 도착시각으로 한다. 예를 들어 10월 26일 마감 전·납기2일은 10월 28일 00:00 도착이다. 요일·공휴일과 무관하게 모든 날을 센다. 영업일 납기는 별도 검증 전 수용하지 않는다. 마감 지연을 포함한 실제 보호기간이 14일을 넘으면 승인을 차단한다. 날짜별 분위수 합계를 보호기간의 같은 분위수로 해석하지 않는다. 안전재고가 설정되지 않은 품목은 주문안을 진단용으로만 생성하고 승인하지 못하게 한다. 가상 시나리오는 안전재고·납기·포장 환산을 명시적으로 제공하며 기존 연구의 95% 서비스 성과를 보장값으로 쓰지 않는다.

일별 예상재고로 도착 전 부족·늦은 입고·사용불가를 확인한다. 보호기간 총량이 충분하다는 이유만으로 앞선 결품을 무시하지 않는다. 도착 전 부족에 대한 별도 조치가 없는 경우·재고 기준시각이 없거나 오래된 경우·미입고 주문 연결 불명·포장 환산 미확인·자료 정정 중인 경우는 승인 차단 사유다. 초기 정책에서 재고 기준점은 해당 주간 마감 시각이며 이후 사건을 모두 반영해야 한다. 누락 구간이 있거나 첫 수요 처리 시점을 넘기면 재고 재확정 전 승인을 차단한다.

주간 재고 스냅샷은 해당 기준시각의 재고 기준점이다. 이미 반영된 주간 소비나 입고를 다시 차감·가산하지 않는다. 이후 사건만 적용하며, 새 스냅샷과 내부 입고 원장의 차이는 조정 이력으로 남긴다. 외부 미입고 자료는 내부 주문과 원천 주문번호로 연결하여 중복 합산하지 않는다. 입고 취소·정정은 원사건 삭제 대신 반대 사건으로 추적한다.

## 승인과 주문 및 입고 정책

### 승인 범위와 유효성

주문안은 예측 실행·입력 버전·재고 버전·정책 버전·내용 해시·유효기한을 가진다. 가상 시나리오의 승인 유효기간은 생성 후 업무 시각 24시간 이내이면서 첫 보호 대상 수요 처리 전까지로 제한한다. 실제 수신 지연이나 자료 변경이 있으면 더 일찍 만료할 수 있다.

초기에는 전체 주문안에 대한 Yes/No만 지원한다. 품목·수량 수정은 새 버전을 만들고 새 승인을 요구한다. 사용자 권한·주문안 상태·버전·해시·만료·차단 사유를 확인하고, 승인 기록·주문 의도·발주 예약·Outbox를 같은 트랜잭션에서 저장한다. 동시 승인은 주문 범위의 잠금·고유 제약·조건부 갱신으로 한 건만 확정한다.

차단 품목이 있는 주문안 전체는 진단용으로 표시하고 승인하지 않는다. 초기에는 품목 부분 제외를 지원하지 않으며 차단 사유를 해소하고 전체 명단의 새 주문안 버전을 검토한다. No는 거절 이력만 남기며 주문 의도·주문 전송 Outbox를 만들지 않는다. 미응답·만료도 자동 Yes로 전환하지 않는다.

미전송 승인 주문은 이미 확정한 발주 예약으로 관리하여 새 주문안이 같은 부족량을 다시 주문하지 않게 한다. 이 수량은 실제 재고나 공급처 접수 확정 재고와 구분한다. 전송 결과 불명 주문이 같은 품목에 있으면 해소 전 추가 승인을 차단한다. blocked이고 전송을 시작한 이력이 전혀 없는 주문 또는 공급처의 최종 rejected 주문은 상세 API의 release로 종료·예약 해제한 뒤 재계산한다. accepted·sending·결과 불명 및 단순 미접수 조회만 확인된 주문은 이 경로로 해제하지 않는다.

### 전송과 접수

주문 상태는 `pending_send → sending → accepted / submission_unknown / rejected`로 구분한다. 승인 기록의 `approved`와 공급처의 `accepted`는 다르다. 가상 공급처는 영속 주문 키별 중복 방지·키 조회·동일 키에 다른 내용 거절을 지원해야 한다.

업무 실행기는 전송 직전 승인·만료·입력 정정·관련 재고 및 주문 변경을 다시 검사한다. 자신의 발주 예약은 새 외부 변경으로 보지 않도록 기준을 구분한다. 영향이 있으면 수량을 몰래 바꾸지 않고 전송을 보류하여 새 주문안과 승인을 요구한다. 전송 선점은 승인·만료 처리와 경쟁하지 않도록 짧은 DB 트랜잭션으로 확정하고, 외부 통신 동안 DB 잠금을 유지하지 않는다.

공급처 접수 후 응답 유실·프로세스 종료·DB 저장 실패는 `submission_unknown` 또는 미해소 전송 시도로 남긴다. 영속 주문 키로 먼저 조회하고, 접수되었으면 같은 주문에 연결한다. 미접수가 확인되어 재전송하더라도 동일 키·동일 내용만 사용한다. 이미 전송을 시작한 주문은 새 자료 제출로 자동 취소하지 않는다.

입고는 주문 상태와 구분하여 `not_received / partially_received / received`로 관리한다. 입고 사건 키를 유일하게 유지하고, 수량·단위·미입고 잔량·기준시각을 검사한 뒤 입고 이력과 재고 변경을 같은 트랜잭션으로 확정한다. 주문 취소는 공급처 취소 확인 절차가 정의되기 전 자동화하지 않는다.
