## 검토 범위와 독립성

대화 이력을 전달하지 않은 두 에이전트가 작성된 명세를 읽기 전용으로 검토했다. `contract_business_audit`는 주간 업무의 연결과 복구 경로를, `contract_schema_audit`는 API·DB·정책·상태의 교차 정합성을 담당했다. 두 에이전트는 메모리·과거 세션·원자료·runs를 읽지 않았다고 보고했다. 문서 수정과 추가 에이전트 생성도 하지 않았다.

검토 대상은 architect 단계 문서, API_SPEC.md, openapi.json, DATABASE_SCHEMA.md, schema.sql, BUSINESS_COVERAGE.md다. 실행 서비스 코드는 대상이 아니며 API·worker·공급처 연동이 구현되었다고 판단하지 않았다.

## 지적과 반영

중복 지적을 합쳐 12개 사항을 기록한다. 심각도는 이 명세의 업무 무결성과 복구 가능성을 기준으로 한다.

| ID | 심각도 | 지적 | 반영 계약 |
|---|---|---|---|
| R01 | P1 | 전송 보류 주문의 예약이 영구 유지 | release API·voided·미전송/최종 거절 적격성·토큰 무효화·예약 해제 |
| R02 | P1 | 과거 정정 후 최신 원점의 snapshot을 다시 만들 경로 없음 | delivery_impact·input_revised·영향 원점 조회·최신 주간 전체 새 revision 재제출 |
| R03 | P2 | 일별 수요·충족·부족량의 저장 근거 부족 | demand_outcome·요청=충족+부족·과거 처리일 조회·사용량과 잠재 수요 구분 |
| R04 | P2 | 정책은 품목 제외를 허용하지만 API에 제외 입력 없음 | 초기 품목 부분 제외 미지원으로 정책·요청 계약 통일 |
| R05 | P2 | 영업일 납기 수용에 필요한 휴일·마감·도착 계산 부족 | calendar_days만 지원·모든 요일·마감 전후 기준일·도착00:00 고정 |
| R06 | P2 | 미래 입고 또는 기준점 이전 지연 입고가 재고에 중복 반영 | 미래 사건 거절·stock_effect 분리·anchor 이후 사건 재투영·과거 anchor 자동 회귀 금지 |
| R07 | P3 | 마감시각 정규식이 24~29시 허용 | HH 범위00~23으로 제한 |
| R08 | P2 | 정정과 snapshot 봉인 경쟁으로 구 revision이 영향 조회에서 누락 | 동일 scope 선행 잠금·원천 revision 재검사·pending 예측 생성·추론 시작/완료 stale 검사 |
| R09 | P3 | 미전송 voided 예시에 공급처 접수 정보 존재 | accepted_at·supplier_order_ref를 null로 수정 |
| R10 | P3 | 예약 해제 후 응답 잔량0의 계산 의미 불명 | voided/최종 거절 후 해제 주문의 유효 remaining_units=0, 역사 수량 유지 |
| R11 | P2 | 원 입고 이전 역분개·역분개의 역분개가 허용될 수 있음 | applied 일반 원입고만·원입고≤역분개≤현재·원입고1회 역분개 |
| R12 | P2 | stale 예측이 주문안 없이 끝나 시나리오가 영구 advancing | 명시적 CORRECTION_RESUBMISSION_REQUIRED·대체 파이프라인·주차1회 확정·실패 시 진행 없음 |

R01·R02의 복구 경로는 기존 예측·승인·주문 기록을 삭제하지 않는다. R06의 기준점 이전 입고 자동 역분개와 R04의 품목 부분 제외는 지원 범위를 명시적으로 제한한다. 이를 구현 완료 기능으로 표시하지 않는다.

## 재검토 결과

스키마 검토자는 마지막 재검토에서 잔여 P1·P2·P3를 발견하지 못했다고 보고했다. 업무 검토자는 R12 수정까지 확인한 뒤 검토 범위에서 잔여 P1·P2를 발견하지 못했다고 보고했으며, impact.resolved 시점을 대체 파이프라인 완료로 통일하라는 문구 지적을 남겼다. 해당 문구도 T08과 일치하도록 정리했다.

이 결과는 문서·계약 검토의 범위다. 모든 가능한 장애나 구현 결함이 없다는 보장이 아니며, 실제 HTTP 요청·큐·모델·주문·입고의 실행 검사는 후속 구현에서 수행해야 한다.

## 작성자가 수행한 구조 검증

정확한 검사 대상의 SHA-256·개수·단언 목록은 [구조 검증 결과](validation_results.json)에 보존한다.

| 검사 | 결과와 한계 |
|---|---|
| OpenAPI 3.1 검증 | 35개 operation·33개 path·62개 객체 schema의 규격 검사 |
| 요청·응답 예시 | 성공·오류·요청 예시301개를 JSON Schema와 format 검사로 검증 |
| 합성 제출 예시 | usage210행·patient483행·재고30개, 품목/특징×날짜 중복 없음 |
| API와 DB 연결 | operation의 x-tables가 실제 구조 SQL의 테이블을 참조하는지 검사 |
| PostgreSQL 구조 | 외부 네트워크·호스트 포트가 없는 임시 PostgreSQL 18.6에서 DDL 적용, 테이블46개·FK128개 생성 |
| 범위 FK | 다른 scope의 제출·품목을 연결하는 쓰기 거절 |
| 제출 중복 | 동일 revision·품목·날짜 수량 중복 거절 |
| 수량·관측 상태 | 미관측0·음수·NaN 거절 |
| 봉인 입력 | sealed 부모 변경·자식 추가 거절 |
| Yes/No | reject 결정에 대한 주문 FK 거절 |
| 입고 관계 | 다른 주문의 라인을 입고에 연결하는 FK 거절 |
| 전역 생성 중복 | 신규 scope 생성 요청의 전역 멱등키 중복 거절 |
| RLS | 비관리 역할의 자기 scope 조회·다른 scope 비노출 |
| 문서 정합성 | 상대 링크·코드 블록·operation별 본문 존재·JSON 예시 검사 |

DB 제약 검사는 12개 단언이며 테스트 데이터는 합성 식별자와 임시 트랜잭션만 사용했다. 연구 DB·원자료·환자 행을 적재하지 않았다. 임시 DB 검사는 역할별 GRANT·실제 인증·서비스 함수·부하·장애 복구의 통합 검사를 대신하지 않는다. 사용한 컨테이너는 검사 후 제거한다.

## 후속 구현의 종료 조건

BUSINESS_COVERAGE의 B01~B35와 T01~T09를 서비스 구현과 검사에 연결한다. 구현 후에는 같은 업무 추적표에 실행 테스트 근거를 추가하고, 문서 반영·구조 제약 확인·실제 업무 동작 확인을 별도 상태로 기록한다. 독립 검토에서 확인한 복구 경로도 장애 주입 검사에 포함한다.
