## 배포와 보안 및 자원 정책

서버 이전 묶음에는 고정 이미지 digest·지원 CPU 아키텍처·Compose·환경변수 예시·migration·RabbitMQ 선언·복구 절차·모델 manifest를 포함한다. 비밀값은 이미지·Git·로그에 넣지 않는다. 설정과 자격정보는 서버에서 주입한다. API만 외부 접점을 제공하고 DB·브로커·관리 화면은 내부 네트워크로 제한한다. 승인자·자료 제공자·조회자의 권한을 구분한다.

PostgreSQL·RabbitMQ·비공개 파일 볼륨을 영속화한다. 기존 `data/raw/`와 `data/processed/cheonan/original/`을 컨테이너 쓰기 대상으로 마운트하지 않는다. 신규 가상 자료는 향후 `data/processed/cheonan/analysis/<synthetic_dataset_id>/`, 평가 산출물은 `runs/cheonan/<synthetic_run_id>/`에 manifest와 함께 분리한다. 서버 볼륨의 동일 논리 경로를 배포 설정으로 매핑하며 데이터·모델·산출물을 새로 Git에 추가하지 않는다.

CPU 기본 프로필과 CUDA 선택 프로필을 구분한다. 기존 MPS 코드를 그대로 Linux에 배포하지 않는다. 3~5개 합성 채널에서 형상·마스크·미래 변경 불변성·실행시간·최대 메모리를 확인한 뒤 20·10채널을 검사한다. 하드웨어 확인 전 임의 RAM·GPU 용량을 보장하지 않는다. 모델 메모리 한도를 배포 전 측정하고 API·DB·브로커의 여유를 남긴다.

의존성 readiness 확인·재연결·지수 후퇴·정상 종료를 구현한다. 종료 시 신규 작업 수신을 멈추고 현재 결과를 확정하거나 작업 lease가 복구되게 한다. Compose의 시작 순서만으로 실행 중 장애 복구를 대체하지 않는다. [Compose 단일 서버](https://docs.docker.com/compose/how-tos/production/), [시작과 종료 순서](https://docs.docker.com/compose/how-tos/startup-order/)

가상 평가의 백업 목표는 완료 주간마다 생성하고 별도로 하루 1회 수행하는 것이다. 초기 목표 RPO는 최대 24시간, RTO는 1영업일이며 복원 실험 전 달성했다고 표현하지 않는다. 백업에는 DB·원본·봉인 입력·모델 manifest를 연결한다. 복원 후 큐를 새로 구성해도 DB 작업·Outbox에서 미완료를 복구하고, `sending / submission_unknown` 주문은 공급처 키 조회 후 처리한다. 다른 시점의 DB·큐 백업을 조합해 주문을 무조건 재전송하지 않는다.

## 장애 검증과 완료 기준

아래는 구현 후 수행할 수용 검사다. 현재 통과한 검사 목록이 아니다.

| 검사 | 기대 결과 |
|---|---|
| 동일 제출·테스트 버튼 중복 클릭 | 동일 작업을 반환하고 수량·주차 중복 증가 없음 |
| 반복 사용기록·관측 0·미관측 | 실제 반복 수량 보존, 0과 미관측 구분 |
| DB 커밋 후 브로커 중단 | Outbox 대기, 복구 후 처리, 입력 유실 없음 |
| 발행 확인 후 전달자 종료 | 같은 메시지 재발행에도 결과 중복 없음 |
| 추론 중 자료 정정 | 기존 입력·결과 불변, 새 버전과 새 실행 생성 |
| 모델 실행기 강제 종료·lease 만료 | 유효 시도 복구, 이전 시도 결과 확정 거부 |
| 승인 동시 요청·만료·재계산 | 한 번의 유효 승인만 주문 의도 생성 |
| 공급처 접수 후 응답 유실 | 결과 불명 보존·키 조회, 중복 주문 없음 |
| 부분 입고·동일 입고 재전달 | 재고 한 번 반영·잔량 일치 |
| 스냅샷과 입고 이력 중첩 | 이미 포함된 소비·입고를 이중 적용하지 않음 |
| 로거 중단·DB 장애·로그 폭주 | 유한 버퍼·큐, 업무 재개 가능, 유실 정책 준수·재귀 로그 없음 |
| Linux CPU/CUDA 실행 | 지원 장치별 결과 형상·유한값·자원 확인 |
| 6주 연속 가상 업무 | 승인→발주→입고·잔량 일관성, No·미응답은 주문 없음 |
| 백업·복원·큐 재구성 | 입력·작업·주문 연결 보존, 불명 주문 확인 후 재개 |

관측 항목은 마지막 입력 주간·성공 예측·작업 대기시간·heartbeat·Outbox 지연·결과 불명 주문·로그 적체 및 생산자 폐기 요약·DB/디스크/ML 메모리다. 로그가 사라져도 작업·주문 상태는 DB 조회로 확인할 수 있어야 한다.
